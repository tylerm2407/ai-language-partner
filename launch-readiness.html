Any signed-in user could grant themselves the top paid tier

Fixed

Found inside the "performance" pile. The policy "Users read own subscription" was FOR ALL with USING (auth.uid() = user_id) and no WITH CHECK. For a FOR ALL policy Postgres falls back to the USING expression as the check — and that expression stays true when you change your own row's tier, because it only constrains user_id.

With table-level INSERT/UPDATE grants to authenticated and no trigger on the table, this was directly exploitable:

update subscriptions set tier='vip', is_active=true where user_id = auth.uid();

Why it costs money: get_effective_limits() reads that row to set daily AI quotas, so a user could self-grant unlimited paid-model usage. Migration 057 drops the writable policy, replaces it with SELECT-only, and revokes the INSERT/UPDATE/DELETE grants. Verified by simulating a real user session: the escalation now returns permission denied for table subscriptions.

api_cache was world-writable — burst limits were bypassable

Fixed

A policy named "Allow service role full access to cache" was actually declared FOR ALL TO public USING (true) WITH CHECK (true). The name was a lie: public means every role, so any signed-in user could read, write, and delete the whole table.

api_cache is the burst rate-limit store — increment_rate_limit() keeps its counter there under burst:<action>:<user_id>. So a user could reset their own burst window at will, defeating every AI rate limit including the get-hint one added earlier today.

Fix: migration 056 drops both policies. Only service-role code touches this table, and service_role bypasses RLS, so RLS-on-with-no-policies is correct — matching hint_cache and translation_cache. Verified as an authenticated user: 0 rows updatable, 0 deletable, INSERT rejected.

Stripe webhooks were being rejected before the handler ran

Fixed

Found while preparing the deploy, and not in the original audit. stripe-webhook was deployed with verify_jwt: true and had no entry in supabase/config.toml. Stripe cannot present a Supabase JWT, so the platform gate returned 401 on every webhook — the signature check inside the function never executed.

Fix: added explicit verify_jwt = false entries for stripe-webhook and revenuecat-webhook and redeployed. Auth is now the Stripe signature check, which is the correct control for this path. Verified live: the function is at version 36 with verify_jwt: false.
