Why the webhook test wasn't enough

revenuecat-webhook/index.ts:114 returns 200 for TEST events before it touches the database. A green test tells you RevenueCat can reach the function and the shared secret matches. It tells you nothing about whether the upsert works.

The failure this catches

A purchase succeeds, RevenueCat grants the entitlement, and the app unlocks — because the client reads RevenueCat directly. But the webhook never lands, so subscriptions still says starter. The customer pays, sees premium features, and immediately hits free-tier rate limits. Everything looks fine from the outside.

Before you build

All four must be true. Skip one and the paywall renders empty, which costs you a full build cycle to discover.

Paid Apps Agreement is active

App Store Connect → Business → Agreements

If this doesn't read Active, in-app purchase products never become available and getOfferings() comes back empty. Banking and tax forms must be complete too.

This is the single most common reason a first sandbox test fails.

All six products exist

App Store Connect → your app → Subscriptions

Product IDs must match lib/purchases.ts:14-19 exactly.

fluenci_basic_monthlybasic
fluenci_basic_yearlybasic
fluenci_premium_monthlypremium
fluenci_premium_yearlypremium
fluenci_vip_monthlyvip
fluenci_vip_yearlyvip

Each needs a price, a localized display name and description, and a review screenshot. Status should read Ready to Submit.

RevenueCat is wired end to end

app.revenuecat.com → your project
  • Products imported from App Store Connect — this uses the shared secret you set
  • Three entitlements exist: basic, premium, vip — lowercase, spelled exactly
  • Each product attached to its entitlement per the table above
  • An Offering containing those packages, marked Current
Easy to miss

getOfferingPackages() reads offerings.current (lib/purchases.ts:107). With no offering marked Current the paywall is empty even when every other piece is correct.

A sandbox tester account exists

App Store Connect → Users and Access → Sandbox → Test Accounts

Use an email that has never been an Apple ID. A plus-alias works well — tcm2407+sandbox1@gmail.com. Set a password and save it; you'll retype it several times.

Ignore the verification email Apple sends. Verifying it can convert the address into a real Apple ID and break the tester.

Running the test

Order matters — each step sets up the one after it. Steps 1 to 6 happen on your device and in dashboards; 7 to 9 are terminal checks I can run for you.

1

Build for a real device

Terminal

In-app purchases don't work in Expo Go or the simulator — the native StoreKit module isn't there. 

npx eas build --profile preview --platform ios

The preview profile now carries the real appl_ key and builds Release with internal distribution. Install on your iPhone via the QR code EAS returns.

If your device isn't registered for internal distribution yet, run npx eas device:create first.

2

Sign in to the sandbox account

On device

This is separate from your real Apple ID — you do not sign out of your normal account. 

Settings → App Store → (scroll to bottom) → Sandbox Account → Sign In

If a previous tester is already listed, sign out first. A stale sandbox account silently attributes the purchase to the wrong tester.

3

Sign in to Fluenci and capture your user id

On device Terminal

Sign in with a normal Supabase account, then pull the UUID. This is the value that has to show up as app_user_id in RevenueCat. 

npx supabase db psql -c "select id, email from auth.users where email = 'YOUR_TEST_EMAIL' limit 1;"

Keep that UUID somewhere handy — steps 6, 8 and 9 all need it.

4

Open the paywall

On device

Navigate to the subscription screen — app/(app)/profile/subscription.tsx.

Checkpoint

Packages render, with real prices.

If the list is empty, stop here

The problem is in the prerequisites, not your app code. Almost always either the Paid Apps Agreement isn't active or no offering is marked Current.

5

Buy a plan

On device

Pick VIP monthly — the highest tier makes tier resolution unambiguous all the way down the chain.

Confirm before you authenticate

The confirmation sheet must say [Environment: Sandbox]. That's your proof no real money moves. If it's missing you're on your real Apple ID — cancel and redo step 2.

Checkpoint

The UI unlocks. That proves the client half: tierFromCustomerInfo() read an active vip entitlement straight from RevenueCat.

6

Confirm RevenueCat filed it under the right user

Dashboard

RevenueCat → Customers → open the newest customer.

Checkpoint

Customer ID equals the Supabase UUID from step 3 — not $RCAnonymousID:….

If you see an anonymous ID

revenuecat-webhook/index.ts:108 drops any event whose app_user_id isn't a valid UUID. It means configurePurchases() ran before the user signed in — and no purchase will ever reach your database. Fix this before continuing; the remaining steps can't pass.

7

Confirm the webhook fired and succeeded

Terminal 
npx supabase functions logs revenuecat-webhook --project-ref ngqpsuixmumdnqbqxjxv
Checkpoint

A POST returning 200, within seconds of the purchase.

What you seeWhat it means
401The Authorization header value in RevenueCat doesn't match the secret. Re-paste it.
500 · "REVENUECAT_WEBHOOK_AUTH is not set"The fail-closed path. Shouldn't happen now that the secret is set.
500 · "subscriptions upsert failed"Auth is fine, the database write broke. The real error is on that log line.

Webhook URL: https://ngqpsuixmumdnqbqxjxv.supabase.co/functions/v1/revenuecat-webhook

8

Confirm the database row

Terminal 
npx supabase db psql -c "select user_id, tier, is_active, subscription_status, current_period_end, cancel_at_period_end, updated_at from public.subscriptions order by updated_at desc limit 3;"
Checkpoint

A row for your UUID with tier = 'vip', is_active = true, subscription_status = 'active', and a current_period_end a few minutes out — sandbox subscriptions run on a heavily accelerated clock.

9

Confirm server-side enforcement

Terminal

The step people skip, and the one that catches the paid-but-rate-limited bug. get_effective_limits is what every quota check actually reads. 

npx supabase db psql -c "select public.get_effective_limits('YOUR_UUID_HERE'::uuid);"
Checkpoint

VIP-level quotas come back, not starter ones.

If step 8 passed but this returns starter limits

The bug is inside get_effective_limits itself — most likely a tier string it doesn't recognise. This is exactly the split-brain state the whole test exists to find.

10

Restore purchases

On device

Delete the app entirely. Reinstall from the same EAS link. Sign in with the same Supabase account.

Checkpoint

You start locked out. Open the subscription screen, tap Restore Purchases (subscription.tsx:105), and access comes back.

Not optional

Apple requires a working restore path. A missing or broken one is a documented rejection under Guideline 3.1.1, and reviewers do test it.

Worth doing while you're set up

Sandbox subscriptions run on a compressed clock — a one-month subscription renews roughly every five minutes and auto-cancels after six renewals. The renewal and expiry paths are nearly free to test.

  • Wait for a renewal, then check the logs for a RENEWAL event and confirm current_period_end moved forward.
  • Let it run to auto-cancellation and confirm an EXPIRATION event flips tier to starter and is_active to false.
Known issue you won't reproduce here

BILLING_ISSUE sits in INACTIVE_EVENTS (index.ts:52), so it revokes access immediately. In production Apple fires that at the start of a billing problem, while the store grace period may still entitle the user — so a customer whose card hiccups gets downgraded while legitimately paid up. Worth fixing before launch. It does not block this test.
